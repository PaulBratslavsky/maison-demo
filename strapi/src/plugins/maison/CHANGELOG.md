# Changelog

## Unreleased

### Added

- **Demo customers get no LINE message.** Load demo activity's five made-up customers have LINE user IDs that belong to nobody, so LINE refused every message to them, and the board showed red failures on stage. Now `isDemoCustomer(subject)` (in `server/src/domain/demo-activity.ts`, the subjects in `activity.json`) is checked before every push: the confirmation (the publish hook and Send again), Let them know, Answer and Reply on LINE skip the push for them, with or without a token, and record the new outcome `demo`, with the detail "Demo customer: no LINE message". Everything else the action does still happens.
  - `notification.outcome`, `question.lineOutcome` and `inquiry.lineOutcome` take `demo`. Enumerations are stored as text, so the database needs no change.
  - The actions answer 200 with `status: "demo"`. The board's LINE column says "demo customer" in grey, with no Send again, and Confirm's notice says "Confirmed APT-1234. Demo customer: no LINE message." The questions and inquiries show "Demo customer: no LINE message." in grey under their status, never in red. `StaffAppointmentView` and the requests summary's rows have a new `demoCustomer` field, and so does `staffAppointmentOutput`.
  - A `demo` outcome is never pending (`pending_confirmations` lists none, and counts only `failed` records as earlier attempts), and "LINE sent" doesn't count it. `confirmations.record` returns the first `demo` record for a second one, as it does for `sent`.
- **`demoLineUserId`, your own LINE account for three demo items.** An optional setting, from `MAISON_DEMO_LINE_USER_ID`: a LINE user ID, `U` and 32 lowercase hex characters. Any other value is ignored, with a warning that names the setting and never the value, so an optional demo setting never stops Strapi starting. With it, Load demo activity gives that account the three items marked `"owner": "you"` in `activity.json`: one waiting request, one open question and one open complaint. They're real LINE sends: confirming, Let them know, Answer and Reply on LINE message your phone. The question is named with your LINE display name when Strapi has a token. If your account has as many open requests as a customer may have, your request stays with its made-up customer, and the log says so. The load's guard still counts only the five made-up customers. The value is never logged, and the admin masks it like every customer. `appointments.countOpenRequests(subject, now)` is the rule `request` holds against the limit.
- **A "Your LINE" label on your own rows.** With `demoLineUserId` set, the rows of your LINE account carry a small "Your LINE" badge next to the masked customer: on the requests board and in the Requests widget, under Questions, and under Inquiries (the question's hand-off and the complaint). Its title reads "Replies and confirmations for this customer go to your own LINE account." On stage, it tells your rows, whose confirmations and replies reach your phone, from the made-up customers' rows, which get no message.
  - `isYourLine(subject, demoLineUserId)` in `server/src/domain/demo-activity.ts` is the rule: the setting is set, and the subject is `line:` followed by exactly that ID. It is false for every subject when the setting is unset or ignored.
  - `StaffAppointmentView` (and the requests summary's `recent` rows), `StaffQuestionView` and `StaffInquiryView` have a new boolean `yourLine`, and so does `staffAppointmentOutput`, next to `demoCustomer`. The ID itself is in no view, log or answer.

### Changed

- **Load demo activity answers at once and finishes in the background.** On Strapi Cloud a press took about 28 seconds, one write after another against the remote database, and Cloud's proxy gave up with an HTML page, which the page showed as a JSON parse error.
  - `POST /maison/demo/activity` first checks whether the activity is there and plans the visits, which only reads, so errors such as "load the catalog first" still come back on the press. Then it answers `202` with `{ started: true, appointments, questions, inquiries }` and writes in the background, or `200` with the "already there" result when there is nothing to add.
  - The writes run as three groups side by side: the visits (each request, its confirmation, then when it came in), the questions (each with its hand-off, one after another, so each new reference is checked against the questions already written), and the standalone inquiries.
  - A press while a load is still running answers `409` with the new error code `already_loading`, and starts nothing. A failure in the background is logged as an error that says to press Reset demo activity, then Load demo activity again, and never stops Strapi.
  - The two confirmed visits now record `demo` with no LINE call.
- **Load demo catalog answers at once too.** It reads what is missing first, answers `200` with all zeros when everything is there, and otherwise `202` with `started: true` and what it will add, then writes in the background. The 16 Japanese versions are written four at a time, each one's update then publish in turn. A press while it loads answers `409` `already_loading`. `npm run setup` presses again every second until everything is there.
- **The Demo data buttons** show "Loading demo activity: the lists fill in over the next few seconds." for a 202, refresh the lists again a few seconds later, show "Strapi took too long to answer. Wait a few seconds: the lists refresh by themselves." for an answer that isn't JSON, instead of the parse error, and show "already loading" as an info notice.
- The appointment entry's Japanese keywords no longer list ブティック twice. No search result changes.

- **Product knowledge in Japanese.** Each of the 16 seeded entries has a Japanese version, in a client advisor's polite register, with the same facts as the English, the catalog's Japanese product names, and Japanese keywords for the search. A Japanese chat's `search_knowledge` now answers care and policy questions from them, instead of handing every one to staff.
  - The content is in `server/seed/knowledge.json`, each entry's Japanese title, answer and keywords under `ja`.
  - **Load demo catalog** adds the English entries when there are none, as before. Then it finds each entry's English document by its English title, and when that document has no Japanese version, adds one with the Document Service (`update` with `locale: 'ja'`, then `publish` in `ja`). The category and products are shared, so Strapi copies them from the English version. A Strapi that has only the English entries gets the 16 Japanese versions. Pressing it again adds nothing, an entry whose English title staff changed is skipped, and the entries staff added by answering questions are never changed. The English entries stay as they are.
  - `POST /maison/demo/seed` also answers `knowledgeJa`, the Japanese versions it added, and the notice names both languages: "Added 16 product knowledge entries in English and 16 in Japanese." `npm run setup` says the same.
  - Reset demo activity keeps the seeded product knowledge in both languages.

- **Load demo activity,** a button beside Load demo catalog under Demo data, adds five made-up customers' activity for the Maison page to show: five visit requests (three waiting for staff, two confirmed), five questions (three open, one taken, one answered) and ten inquiries (each question's hand-off, two complaints, one praise, one question answered from product knowledge, and one left for the labelling sweep), received over the last three days.
  - The customers have fixed LINE user IDs that belong to nobody (`line:Udec0de`, zeros, then a digit), and display names. Staff see them masked.
  - The requests go through the appointments service, so they get `APT-` references and pass its checks. Each is 2 to 13 days ahead, on a half-hour inside its boutique's opening hours (never Osaka on a Tuesday), for pieces the boutique has in stock when the button is pressed. The two confirmed ones are published as the board's Confirm does it, so the LINE confirmation hook runs and records what LINE answers.
  - The questions get `Q-` references from the questions' generator, now exported as `uniqueQuestionReference`. None has a LINE outcome or a knowledge entry. The seeded labels have `modelVersion: 'demo-seed'` and no `promptVersion`, and each queue comes from `queueFor`. `sentimentLabelOf` gives a score's label by the labelling prompt's thresholds.
  - It adds the set only when none of the five customers has an appointment, a question or an inquiry, so a second press changes nothing, and other customers' activity never counts or changes. A press while one is loading waits for it. Without the demo catalog it adds nothing and answers 404. Reset demo activity deletes it with everything else.
  - `POST /maison/demo/activity`, gated by "Load and reset demo data" like `/demo/seed` and `/demo/reset`, answers `{ created, customers, appointments, confirmed, questions, inquiries }`. The page shows it as a notice and reloads its lists.
  - The content is in `server/seed/activity.json`.
- **Customer inquiries: every concierge turn is recorded, a model labels it in the background, and staff work the queues and reply on LINE.** A proof of concept, built on the customer questions below.
  - `log_inquiry` (MCP: log customer inquiries) records one concierge turn for the signed-in customer: their message and the concierge's reply, whether knowledge was found, whether the turn handed the question off, and optionally the question the hand-off recorded, the piece and the chat's language. The app's server calls it after each turn. The text keeps its line breaks, the message cut to 1,000 characters and the reply to 2,000. An existing customer token needs the new permission, and the admin chat doesn't offer the tool.
  - A new content type, `plugin::maison.inquiry`, hidden from the Content Manager and the Content-Type Builder because it holds customers' LINE IDs, and an `inquiries` service.
  - **Labelling.** A cron job, `maison-label-inquiries`, runs every minute and labels up to 10 inquiries, oldest first, through the AI SDK: a kind (question, complaint, praise or other), a sentiment, whether the concierge answered, and the model's reason and topic, in English. The prompt treats the customer's text as evidence, not instructions. A failure that is about the inquiry (a model that answers in the wrong shape, the provider rejecting that inquiry's own text, a failed save) fails it with nothing half-written saved, at most 5 times, and **Label again** puts it back. The sweep goes on with the next inquiry. A refused key or setup (401, 403 or 404, which a wrong key or model name gives) or no answer from the model (a timeout, a dropped connection, a provider that is down) counts nothing: it leaves the inquiry as it was and ends that sweep with one warning, so a wrong key or model name or a dropped network parks nothing.
  - **New config:** `aiProvider` (`anthropic`, `openai` or `openai-compatible`), `aiModel`, `aiApiKey` and `aiBaseUrl`, read from `AI_PROVIDER`, `AI_MODEL`, `AI_API_KEY` and `AI_BASE_URL`. The default is Claude Haiku 4.5. **Without a key, nothing is sent to a model:** new inquiries are marked `skipped` and wait under Not labelled, and the sweep labels them once a key is set. The plugin now needs Node 22.12 or later, which the AI SDK needs.
  - **Queues, by code.** A hand-off, or a question nobody has said was answered, is in Needs an answer (a question a person labels by hand counts: with AI off, it is the likeliest label), a complaint is in Complaints, and praise is in Praise. A person's label wins over the model's.
  - **An Inquiries tab on the Maison page,** for admins with the new permission "Review customer inquiries". It refreshes every 5 seconds, and shows four cards that count the open inquiries (Needs an answer, Complaints, Praise and Not labelled), the same five filters as pills, and each inquiry's time, masked customer, message, piece, kind, sentiment and status, with **What the concierge said** for its reply and the model's reason and topic. The messages keep their line breaks, and a long one scrolls in its box. A hand-off shows its question's reference and points to Questions. Above the table, the month's LINE messages, which replies count toward.
  - Admins with the new permission "Reply to customer inquiries on LINE" get **Reply on LINE**, **Close** (Answered elsewhere, Not needed or Spam), **Change label** and **Label again**.
    - **Reply on LINE** opens a dialog with a box that is never pre-filled, and **Use the suggested text** for a complaint or for praise, in English or Japanese. It pushes one LINE text message in Maison's name, quoting the customer's first 80 characters, and marks the inquiry replied. Only customers who have added Maison on LINE get it: LINE answers 200 for anyone else and delivers nothing. The admin's first name is saved on the inquiry and never sent. It is disabled while a request runs.
    - A hand-off is answered under Questions, not here.
    - **Change label** sets the kind, the sentiment or both, and the inquiry is then a person's: the sweep never labels it again. **Label again** isn't offered for it. An inquiry with no kind needs one: a sentiment alone is refused with `invalid_input` ("Pick a kind too."), and **Save label** stays disabled for it, with the same words under **Kind**.
  - **The Maison page has tabs now:** Requests, Questions and Inquiries, each shown to the admins who may see what is in it, with Demo data below them. Each label says how many are waiting in it, like **Questions 2**: the requests waiting for staff, the questions that are open or taken, and the inquiries in Needs an answer, with no number for none. They refresh every 5 seconds, whichever tab is open, and at once after an action. The tab is in the address, so `/plugins/maison?tab=inquiries` (or `questions`, or `requests`) opens it, when the admin may see it, and the first tab they may see opens otherwise.
  - **A second Homepage widget,** "Maison inquiries" (`plugin::maison.inquiries`), for admins with "Review customer inquiries": the four open counts, refreshed every 5 seconds. Its link, Open the inquiries, opens the Inquiries tab. The requests widget is unchanged.
  - **Admin routes:** `GET /maison/inquiries` (with `filter` and `limit`), `GET /maison/inquiries/summary` and `GET /maison/inquiries/quota` (which answers `{ configured, used, limit }`: `configured` is false without a channel access token, and the Reply on LINE dialog then says so and disables **Send on LINE**), and `POST /maison/inquiries/:documentId/reply`, `/close`, `/label` and `/label-again`. A 200 carries the server's `message`, which warns when the customer has the reply but recording it failed. Errors are 400 (`invalid_input`), 404, 409 (`already_closed`, `already_replied`, `use_question` and `not_failed`), 502 when LINE refused the message or couldn't be reached, and 503 without `lineChannelAccessToken`. The new error codes are `already_closed`, `already_replied` and `not_failed`.
  - **Reset demo activity**, as the reset button is called now (it was Reset demo appointments), also deletes every inquiry, however many there are: it reads them again until none are left. `POST /maison/demo/reset` answers `{ appointments, notifications, questions, inquiries, knowledge }`.
- **Customer questions: when the concierge can't answer, staff follow up on LINE.** Strapi records the question, staff let the customer know or answer on LINE in their own name, and an answer can become product knowledge. A proof of concept.
  - `hand_off_to_staff` (MCP: hand questions to staff) records the signed-in customer's question for Maison's client advisors, with the piece it's about and the customer's LINE name when LINE gives one, and answers a reference like `Q-4821`. It sends the customer nothing. A customer can have five questions open or taken at a time: another is refused with the new error code `too_many_open_questions` (MCP only: no REST route hands off a question). An unknown piece never refuses a hand-off. An existing customer token needs the new permission, and the admin chat doesn't offer the tool.
  - A new content type, `plugin::maison.question`, hidden from the Content Manager and the Content-Type Builder because it holds customers' LINE IDs, and a `questions` service.
  - A **Customer questions** section on the Maison page, for admins with the new permission "Read customer questions": it refreshes every 5 seconds and filters to Open, Answered or All. Admins with "Answer customer questions on LINE" get **Let them know**, which sends the customer one LINE message in their first name and takes the question, and **Answer**, a dialog whose **Send on LINE** sends the answer in their name and marks the question answered. With **Add to product knowledge** ticked, the answer is also published as a product knowledge entry in the question's language, with the question's piece as its product and a title staff can edit, the customer's question to start with.
  - `GET /maison/questions`, `POST /maison/questions/:reference/notify` and `POST /maison/questions/:reference/answer`. A 200 carries the server's `message`, which can warn that recording the question failed or that the entry couldn't be made, as the customer has the message by then. Errors are 400, 404, 409 (`already_taken`, `already_answered`), 502 when LINE refused the message or couldn't be reached, which leaves the question as it was, and 503 without `lineChannelAccessToken`.
  - The messages are in the question's language, Japanese or English, quote the question cut to 80 characters, and are signed with the admin's first name, or write for the team without one. The code that pushes to LINE is now shared by confirmations and staff messages. Confirmations are unchanged.
  - **Reset demo activity** also deletes every question and the product knowledge entries their answers added, in every language. The seeded product knowledge stays. `POST /maison/demo/reset` answers `{ appointments, notifications, questions, inquiries, knowledge }`.
  - After review: the Answer dialog shows the knowledge entry's public title as **Title in product knowledge**, for staff to edit (`title` in the answer's body), an admin whose first name is the house's own ("Maison", or either `houseName`) writes for the team, `hand_off_to_staff` answers the existing reference for a question the customer still has with staff instead of recording it twice, and a 200 with `warning: true` shows as a warning.
- **Product knowledge, and `search_knowledge`.** A new content type, `plugin::maison.knowledge`, localized with draft and publish: a title, an answer of up to 2,000 characters, a category, the products it's about (`productSlugs`, empty for every piece) and keywords. Saving one refuses a `productSlugs` that isn't a list of distinct slugs.
  - `search_knowledge` (MCP: browse the catalog) returns the best four published entries for a question, in its locale with the default locale filling in, scored on the question's words in the title, the keywords and the answer, or none. With `productSlugs`, entries about other pieces are left out, and an unknown or unpublished product is `not_found`.
  - `GET /api/maison/knowledge` is the same search over REST, on the action `plugin::maison.knowledge.find`.
  - A question is trimmed before it's checked, so one of only spaces is refused like an empty one: `invalid_input` over REST, and the MCP SDK's own `Input validation error` over MCP.
  - **Load demo catalog** adds 16 product knowledge entries in English, also to a catalog loaded before. Its notice says what it added.
- **Strapi sends the LINE confirmation itself, on every confirm path:** the board's Confirm, `confirm_appointment` in the admin chat or from an MCP client, and Publish in the Content Manager.
  - Once a publish of an appointment has gone through, a document middleware pushes the visit's flex message with LINE's push API and waits for the answer, 8 seconds at most. Inside a transaction, as the Content Manager's Publish runs, it sends once the transaction commits instead, without waiting, and a rolled-back publish sends nothing. A failed send never fails the publish. The new `line-confirmations` service sends it, with the message `pending_confirmations` lists, now built by one shared function.
  - Each attempt is recorded as a notification by `strapi`: sent, or failed with LINE's HTTP status and message. A push LINE took but that couldn't be recorded answers `sent_unrecorded`. A visit gets one, so publishing again sends nothing, two sends at once share one push, and a visit that's over gets none. `confirmations.record()` takes an optional `recordedBy`, and still writes `ops-agent` without it.
  - A new appointment's reference is never one a notification still names, so a new visit can't count as already confirmed over LINE.
  - New config: `lineChannelAccessToken`, from `LINE_CHANNEL_ACCESS_TOKEN`, and `lineApiBaseUrl`, `https://api.line.me` by default. Without a token, Strapi sends and records nothing, and logs a warning once.
  - **Send again** on the board, for confirmed requests not yet sent whose visit is still ahead, through `POST /maison/appointments/:reference/notify`, gated like Confirm.
  - The confirm toast says whether the customer's LINE confirmation was sent, and points to Send again when it wasn't. It and `confirm_appointment`'s description no longer say the ops agent sends the confirmation. The ops agent's tools and prompt are unchanged, for retries.
- **The LINE confirmation is in the language the customer booked in.** An appointment keeps it as `language` (`ja` or `en`, `ja` by default), from the booking's `locale`, or `defaultLocale` without one. Every confirmation follows it, from Strapi or `pending_confirmations`: the words, the house name, the date (`Sat 10 Oct, 14:00` in English, from the new `formatEnDateTime`), and the boutique's name and address and the pieces' names, from their published versions in that language with the default locale's value for a field that's missing or empty. A visit without a `language`, such as one booked before, is Japanese, and a Japanese confirmation is exactly what it was.
- **A "Maison requests" widget on the admin Homepage** (`plugin::maison.requests`), for admins with "MCP: review appointment requests". It counts one pipeline of visits still ahead (the requests waiting for staff, the confirmed visits, and how many of those have had their LINE confirmation sent), lists the five newest requests, and refreshes every 5 seconds.
  - `GET /maison/appointments/summary`, an admin route gated on the same permission as the board's list. It answers `{ counts, recent }` from the new `appointments.summarizeRequests()`, which counts with the board's own definitions and returns the board's "All requests" rows, masked the same way.
- **REST routes at `/api/maison`**, on the same services, input schemas and LINE customer identity as the MCP tools:
  - `GET /collections`, `GET /products`, `GET /products/:slug` and `GET /boutiques`, as `browse_collections`, `search_products`, `view_product` and `find_boutiques`. Their actions are `plugin::maison.collections.find`, `products.find`, `products.findOne` and `boutiques.find`. Grant them to a role such as Public, or call with a read-only, full-access or custom API token.
  - `POST /appointments` and `GET /my-appointments`, as `request_appointment` and `my_appointments`, for the signed-in LINE customer only. A new `customer-session` policy runs `/mcp`'s session check (oauth-mcp-manager's `resolveAccessToken`), then resolves the customer the way the tools do (`resolveSubject`). It answers 401 with `WWW-Authenticate: Bearer` when that check refuses the session or no LINE customer holds it, 503 `not_configured` without oauth-mcp-manager 1.1, and 503 `temporarily_unavailable` when checking the session fails on the server.
  - `/mcp` goes further in two ways. Strapi core also refuses a session whose admin token has expired (`checkExpiry`), which the REST door accepts until the session itself expires, at most the session TTL of 1 hour. And each tool needs its own permission on that admin token, which the REST door doesn't check. Closing the first gap belongs in oauth-mcp-manager (`resolveAccessToken` refusing an expired admin token), in a later release.
  - Errors as `{ "error": { "code", "message", "hint" } }`, with the tools' codes, messages and hints, and statuses 400, 401, 404, 409, 422 and 503. One code is the REST door's own: `temporarily_unavailable`.
- `createdVia: "web"` for visits requested through the REST routes. The requests board, `appointment_requests` and `confirm_appointment` show it.
- `identity.customerSession(authorization)`: the customer behind an `Authorization` header, for the MCP tools and the REST routes alike. It always runs `/mcp`'s session check first. Only the MCP tools skip that step, inside the service, because `/mcp` has already run it on their request.

### Changed

- The warning notice that Let them know, Answer, Reply on LINE and the board's Send again show when the customer has the message but something after it went wrong ("…Don't send it again.") stays on screen until it is dismissed, instead of fading after a few seconds. A success still fades.
- Answering a customer question marks the inquiries its hand-off came from as replied, with the answer, when, and by whom. A failure to mark them never changes the outcome of the answer: the customer has it, and the server logs a warning.
- `request_appointment` takes an optional `locale` (`ja` or `en`), like the other customer tools, and names the boutique and products in its answer in that language. Until now it always answered in `defaultLocale`, which is still the default. The booking body of `POST /api/maison/appointments` takes it too.
- The customer tools' input schemas live in `server/src/mcp/schemas.ts`, shared with the REST routes. Apart from `request_appointment`'s `locale`, the tools' inputs, outputs and errors are unchanged.
- An appointment's `customer`, a full LINE user ID, is kept out of every admin API answer and out of the Content Manager's list search: the schema marks it `hidden` in its config and `searchable: false`, as the question and inquiry content types do. The Content Manager already left it out of its views, and the Document Service still reads and writes it. An app that set these flags itself, in `src/extensions/maison/strapi-server.ts`, can delete that file.
- A failed customer lookup is logged without oauth-mcp-manager's error message, which could quote the token.
- Demo catalog photos from Pexels replace all eighteen generated images. See `server/seed/images/SOURCES.md`.
- The LINE confirmation message uses the app's black-and-white palette: an ink header with the house name in white, grey labels and an ink button, in place of the cream on near-black.
- The Homepage widget shows its three counts as cards and its five newest requests as a table, with when each request came in and the customer's note, and the Maison page shows the same cards above the board, whose rows show the note too. The `recent` rows of `GET /maison/appointments/summary` gain `createdAt` and `note`.
